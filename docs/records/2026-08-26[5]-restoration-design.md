# Восстановление внутри узла: почему одного идентификатора мало

> **Состояние: сделано, вошло в 0.3.0** (не опубликована). Устройство
> `NavigationNode(restorationScopeId:)`, находка пробы — идентификаторов нужно
> два — и то, чего мы намеренно не обещаем. Закрывает последний пункт из
> «What a node does not do», зависевший от нас; из той же семьи, что находка R7
> ревью `2026-08-24[1]-post-extraction-review.md`.

## Откуда взялось

Соседний проект восстановления не просил и не пользуется им нигде — так и
записано в `2026-08-26[1]-observers-design.md`. Взялись по просьбе владельца,
уже после публикации 0.2.0.

## Что показала проба

Пробным тестом, который потом удалён, на полу 3.27.0. Проверялись шесть случаев.

**Пробросить `restorationScopeId` навигатору узла — недостаточно.** Стек не
возвращался:

```
B before: true    B after: false
```

**Не хватало второго идентификатора — у собственной страницы узла.** Маршрут,
запушенный императивно, хранится прикреплённым к той странице, над которой
лежит, а страница без `restorationId` в восстановлении не участвует вовсе.
Проставили — вернулось:

```
B before: true    B after: true
C before: true    C after: true
```

**C — это `restorablePushNamed` через одолженную таблицу маршрутов.** Две
возможности работают вместе, и это не было очевидно: имя строится заново уже
после перезапуска, то есть таблицу приходится одалживать второй раз.

**Два узла с одним идентификатором** ловятся фреймворком громко:
`Multiple owners claimed child RestorationBuckets with the same IDs`. Молчаливой
порчи данных нет, и уникальность — забота приложения, ровно как с `enabled`.

**Два узла с разными идентификаторами** восстанавливаются каждый свой.

**Приложение, не включавшее восстановление**, ломает только тестовый харнесс:
`restartAndRestore()` отказывается работать без корневого бакета. В настоящем
приложении имя узла в этом случае просто не используется — как и
`restorationScopeId` любого `Navigator`.

## Что сделано

Один необязательный параметр, уходящий в два места: навигатору узла и его
собственной странице. Идентификатор страницы — константа `'node'`: её бакет
живёт **внутри** бакета навигатора, поэтому сталкиваться ему не с чем, что
проба и подтвердила (падает идентификатор навигатора, не страницы).

`_pages` пересобирается ещё и тогда, когда `restorationScopeId` появился или
исчез: список страниц — поле, а страница несёт этот идентификатор в себе.

## Чего мы намеренно не обещаем

**Обычный `push` не восстанавливается никогда.** Он несёт замыкание, и это
правило Flutter, а не узла. Если написать «стек внутри узла восстанавливается»
без этой оговорки, получится ровно та беда, которую в этом пакете чинили дважды:
документ шире кода. Поэтому в README, в зеркале, в дартдоке и в CHANGELOG
названы именно `restorablePush` и его соседи.

**Уникальность имён — на приложении.** Узел не может её обеспечить и не
пытается: у него нет способа узнать про соседей больше, чем есть у `enabled`.

## Нагруженность

Каждая половина правки откачена по отдельности, тест назван:

- снят `restorationScopeId` у навигатора → падает «a node restores the stack
  pushed inside it»;
- снят `restorationId` у страницы → падает он же и «a name pushed restorably
  inside a node comes back».

Контрольный тест держит прежнее поведение: без идентификатора узел по-прежнему
начинает с собственной страницы.

## Грабли, найденные по дороге

**Leak-трекер и `restartAndRestore`.** Тесты восстановления оставляют после себя
`TestRestorationManager` и `RestorationBucket` — объекты тестового биндинга,
которые пакет не создаёт и не может утилизировать. Полная сьюта при этом
зелёная (их подчищает биндинг следующего теста), а вот **один такой тест,
запущенный отдельно, роняет `tearDownAll`** — и это сбивает с толку сильнее,
чем стоит. Оба класса перечислены поимённо в `experimentalLeakTesting` этих
четырёх тестов, а не заглушены целиком: утечка чего-нибудь нашего в них
по-прежнему будет поймана.
