## Находки в обещаниях о восстановлении

### Н1. Цепочка областей рвётся молча, а документ называет условие исчерпывающим

**Medium.** `lib/src/navigation_node.dart:216-218`, `README.md:182-185`,
`README.ru.md:186-189`.

Нашли трое независимо: охотник за дефектами (падающим тестом), Flutter-линза
(зонды 20/21/22), Codex.

Дартдок перечисляет условие как единственное: «none of it happens at all unless
the application enables restoration for itself». На деле идентификатор нужен
**каждому узлу и навигатору в цепочке над узлом**. Навигатор без
`restorationScopeId` не получает бакета, его страницы получают
`restorationEnabled = false`, и `_ModalScopeState` оборачивает содержимое в
`RestorationScope(restorationId: null)` (`widgets/routes.dart:1050-1054`).
Внутренний узел находит пустой бакет и восстанавливает пустоту — без
исключения, без предупреждения, без следа в логе.

```
внешний узел с именем           → restored: 1
внешний узел без имени          → restored: 0
простой Navigator без имени     → restored: 0
```

Вложенные узлы — заявленная фигура пакета (урок 6, отдельный абзац в дартдоке
`observers`), и дать имя именно тому узлу, чей стек хочется сохранить, — первое,
что сделает человек. Это правило фреймворка, а не ошибка узла: код делает ровно
то, что должен. Дефект в том, что документ обещает больше. Лечится фразой в
дартдоке, README и зеркале.

**Вердикт: исправлено.** Дартдок `restorationScopeId` кончается теперь абзацем
про цепочку: восстановление доходит до узла по всей цепочке над ним, и каждому
`Navigator` между приложением и узлом — включая другой `NavigationNode` — нужен
свой `restorationScopeId`, а звено без имени выдаёт узлу под собой пустой бакет.
То же в `README.md` и `README.ru.md` последним абзацем раздела про
восстановление, и одной фразой в записи 0.3.0 CHANGELOG.

### Н2. Обычный `push` обнуляет восстановимость всего, что над ним

**Medium.** `lib/src/navigation_node.dart:201-211`, `README.md:169-178`,
`README.ru.md:173-182`, `CHANGELOG.md:3-8`.

Нашёл Codex, по исходнику. **Проверено мной прогоном:**

```dart
restorablePush(A); push(B); restorablePush(C);   // на экране C
await tester.restartAndRestore();
// A=1  B=0  C=0  home=0
```

Пропал не только обычный `B`, но и `C`, запушенный восстановимо. Правило
транзитивное: `_HistoryProperty.update` (`widgets/navigator.dart:5879-5890`)
ведёт флаг `restorationEnabled` вдоль стека и гасит его на первом же
безстраничном маршруте без `restorationInformation` — дальше до следующей
page-based страницы не восстанавливается ничто.

Документы говорят только «an ordinary `push` carries a closure and is never
restored», и это читается как «потеряется он один». Потребитель, смешавший два
вида пуша, теряет данные там, где документ обещает их сохранить. Ни один тест
дельты смешанный стек не покрывает: обычный и восстановимый пуш проверяются
порознь.

**Вердикт: исправлено в документах, тестом не закрыто.** Дартдок, оба README и
CHANGELOG получили абзац «An ordinary `push` costs more than itself» с тем же
объяснением, а README и зеркало — пример из трёх строк. Теста на смешанный стек
не добавлял: это правка документов, а не кода. Сценарий записан в
`docs/handoff.md` как непокрытый.

### Н3. `restorablePush` не восстанавливается на Web вообще

**Medium для web, Low иначе.** Те же места, что у Н2.

Нашёл Codex. Подтверждено исходником: `_AnonymousRestorationInformation`
переопределяет `isRestorable => !kIsWeb` (`widgets/navigator.dart:5808-5809`,
с ссылкой на flutter/flutter#33615); собственный тест Flutter на восстановление
`restorablePush` в браузере пропущен. `restorablePushNamed` этим не затронут:
`_NamedRestorationInformation` наследует базовое `isRestorable => true`.

То есть на Web ровно тот вызов, который дартдок называет первым, молча не
работает, и `@pragma('vm:entry-point')` тут ни при чём. Оговорки нет ни в
дартдоке, ни в README, ни в зеркале, ни в CHANGELOG.

**Вердикт: исправлено.** Во всех четырёх местах теперь сказано, что в вебе
`restorablePush` не восстанавливает ничего, что пометка `vm:entry-point` этого
не меняет и что `restorablePushNamed` это не затрагивает — имени ссылка не
нужна. README и зеркало ссылаются на flutter/flutter#33615.

### Н4. «Фреймворк скажет сам» — только в debug

**Low.** `lib/src/navigation_node.dart:213-216`, `README.md:180-182`,
`README.ru.md:184-186`, `CHANGELOG.md:8-10`.

Нашли все четверо, независимо. Обещание «the framework says so … **rather than
quietly mixing one stack into the other**» держится проверкой целостности,
которая целиком живёт внутри ассерта: `assert(_debugAssertIntegrity())` в
`RestorationBucket.finalize()` (`services/restoration.dart:835`, сам метод
`:857`). В profile и release ассертов нет, и работает только `_addChildData`
(`:906-918`): второй претендент получает пустой бакет, который в `_rawChildren`
не попадает никогда. В собранном приложении столкновение имён — это молчаливая
потеря стека одного из узлов, ровно то, чего документ обещает не бывает.

В debug обещание правдиво — воспроизведено:
`Multiple owners claimed child RestorationBuckets with the same IDs … "same" was
claimed by: NodeNavigatorState#f3cbe … NodeNavigatorState#3e47f (current
owner)`.

Рядом, про наблюдателей, README точен — «an assertion says so»; здесь той же
аккуратности не хватило.

**Вердикт: исправлено.** Обещание сведено к правде: отладочная сборка говорит
сама, но проверка остаётся ассертом, и релизная сборка молча теряет один из двух
стеков. Так теперь в дартдоке, обоих README и CHANGELOG.

### Н5. Правило «два узла на одном маршруте — два имени» шире кода

**Low.** `README.md:180`, `lib/src/navigation_node.dart:214`, `CHANGELOG.md:8`,
`README.ru.md:184`.

Прогон ревьюера документов: два **соседних** узла с одним именем — обещанное
сообщение; два **вложенных** с тем же одним именем — работают, внутренний
претендует на бакет уже из бакета страницы внешнего. При этом словарь пакета
сам считает вложенные узлы стоящими на одном маршруте (`README.md:268`).
Дартдок формулирует верно в первой половине фразы («unique among everything
that claims a bucket from the same scope»), README эту оговорку потерял и
оставил только вывод.

**Вердикт: исправлено.** Правило названо целиком во всех четырёх местах: имя
уникально среди всего, что претендует на бакет из одной области; двум узлам бок
о бок на одном маршруте нужны два имени, вложенному узлу — нет, он претендует на
бакет из страницы того узла, что над ним.

### Н6. Имя страницы узла стало частью формата сохранённых данных

**Low.** `lib/src/navigation_node.dart:1176`.

Нашла Flutter-линза. На восстановлении фреймворк ищет безстраничные маршруты по
ключу `'p+node'` (`widgets/navigator.dart:3077-3086`,
`_HistoryProperty.restoreEntriesForPage`). Переименуй `_nodePageRestorationId` в
следующей версии — и каждый ранее сохранённый блоб молча отдаст пустой стек: не
ошибку, не предупреждение, а пустой стек. Комментарий у константы объясняет,
почему имя ни с чем не столкнётся, но не то, что менять его теперь нельзя.
Стоит одной строки рядом с константой.

**Вердикт: исправлено.** Строка рядом с константой и стоит: имя — часть формата
того, что записано, фреймворк ищет маршруты под `p+node`, и переименование
оставит каждый блоб прежней версии восстанавливать пустой стек, молча.

## Находка о покрытии, разрешившая спор двух ревьюеров

### Н7. Ветка `didUpdateWidget` нагружена, но не держится ни одним тестом

**Low.** `lib/src/navigation_node.dart:302-310`.

Ревью тестов назвало условие про смену null-ности мёртвым кодом, объяснив это
тем, что `NavigatorState` не зовёт `didUpdateRestorationId()`. Flutter-линза
утверждала обратное. **Правы обе наполовину, и проверено мной прогоном:**

- механизм: `RestorationMixin.didUpdateWidget` **зовёт** `didUpdateRestorationId()`
  сам (`widgets/restoration.dart:869-871`), так что переименование
  идентификатора узел обрабатывать не обязан — тут права Flutter-линза;
- но ветка в узле не про переименование, а про смену **null-ности**: от неё
  зависит `restorationId` собственной страницы узла, а `Page.restorationId`
  финальный, и `Navigator.didUpdateWidget` сравнивает списки страниц по
  идентичности. Убрал ветку — включённый на живом узле идентификатор перестал
  восстанавливать:

```
до мутации:  Q2 (id включён на лету) → A=1
после:       Q2                       → A=0,  при этом сьюта 77/77 зелёная
```

То есть ветка настоящая и нагруженная, а наблюдение ревью тестов («ни один тест
её не держит») верно: это пробел покрытия, а не мёртвый код. Диагноз ревьюера
был неверен, находка — да.

**Вердикт: исправлено.** Тест «a name given to a node already alive still
restores its stack» добавлен в `test/navigation_node_test.dart`: узел поднимают
без имени, дают имя живому, пушат восстановимо и перезапускают. Нагруженность
проверена откатом — без ветки падает он один, остальные 77 остаются зелёными.
Сьюта пакета теперь 78.

### Н9. `9e8ef09` чинил не дефект

**Low.** `example/lib/lessons/l10_restoration.dart:108-122`.

Комментарий утверждает: «starting it here would have this widget call `setState`
in the middle of its own build». `setState` из `initState` ничего не роняет:
элемент в этот момент уже `dirty`, и `markNeedsBuild` выходит по `if (dirty)
return;` раньше любого следствия. Зонд Flutter-линзы (`setState` прямо в
`initState`) — `exception: null`; сьюта урока на `c9bfe0f`, то есть до правки, —
зелёная. Цена правки — лишний кадр `CircularProgressIndicator` при входе в урок;
вред нулевой, но §8 («сперва падающий тест») не соблюдён, а комментарий
утверждает про Flutter неверное. Настоящая причина падения исправлена в
`d0c5046`.

**Вердикт: исправлен комментарий, код оставлен.** Отменять правку я не стал:
она ничего не ломает, а проверить её отмену можно только прогоном настоящего
приложения — а запись `[5]` прямо говорит, что на этом месте трижды чинили не
то. Но оба комментария теперь говорят правду: `setState` при монтировании
фреймворк разрешает и он ничего не стоит (элемент уже `dirty`, и
`markNeedsBuild` выходит раньше следствий), а отложенный старт куплен ради
чтения — чтобы бакет приходил одной дорогой, а не двумя. Второй комментарий
назван тем, что он есть: не лекарством, а страховкой на пути, которого код
урока не достигает.

### Н10. Два теста зелены не по той причине, что написана в их именах

## Что проверено и держится

Дефектов в коде не нашёл никто из пяти. Устойчивым оказалось всё, во что
целились: два узла с разными именами на одном маршруте; узел в узле, оба с
именами, до пяти вглубь с проходом системного «назад» наружу; `restorationScopeId
== null`; смена идентификатора на лету во всех четырёх направлениях и обмен
именами между узлами в одном кадре; подмена бакета под живым узлом; `enabled:
false` до, после и вокруг восстановления; снимок посреди анимации и снос узла
посреди анимации; узел на восстановимо запушенном экране; перенос узла по
`GlobalKey`; закрепление `pop` между двумя восстановлениями; `popUntil`, `pop`,
`maybePop`, системное «назад» и `onPop` с висящим `Future` после восстановления;
наблюдатели вместе с восстановлением, включая молчание собственной страницы
узла; урок 10 под тремя убийствами подряд, с пустым стеком и с двумя нажатиями
в одном кадре. Утечек нет; заглушка leak-трекера безопасна — пакет ни
`TestRestorationManager`, ни `RestorationBucket` не создаёт вообще.

Упаковка в порядке: архив содержит ровно то, что должен, `docs/`, `AGENTS.md`,
`CLAUDE.md` и оба зеркала исключены. Анализатор после `9fd6f00` действительно

## Вердикт

**Кода править не надо: блокеров нет, и ни одна из семнадцати находок не
требует правки в `lib/`.** Все они — либо в том, что документы обещают шире или
точнее кода, либо в покрытии, либо в сопровождающих файлах.

Так и вышло. Правок в `lib/` не понадобилось ни одной, кроме двух комментариев:
дартдок `restorationScopeId`, где обещания сведены к тому, что фреймворк
действительно делает, и строка у `_nodePageRestorationId` о том, что имя стало
частью формата. Прибавилось два теста веса: один новый (Н7) и два переписанных
(Н10), нагруженность каждого проверена откатом. Сьюта пакета — 78.

Что не закрыто и почему — в вердиктах Н8, Н9 и Н17: две правки десятого урока
остаются без теста осознанно, потому что проверить их отмену нечем, кроме
живого приложения, а задвоенный список исключений — правка владельца, и решать
её ему.

**И один гейт остаётся ручным.** `d0c5046` не держится ни одним тестом и не
может держаться: тестовая VM собирает функцию по имени, настоящее приложение —
нет. Перед `dart pub publish` урок 10 надо прогнать на живом приложении с
настоящим убийством процесса — это единственное, что закрывает ту дыру.
