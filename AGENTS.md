# AGENTS.md — точка входа для агентов

Общий регламент работы над пакетом **navigation_node** для Claude Code и
Codex. `CLAUDE.md` ссылается сюда, других точек входа нет.

Правила те же, что в [scopo](https://github.com/vi-k/scopo), откуда пакет
вырос: здесь они пересказаны под один пакет и один пример.

## 1. Начало сессии — восстановление контекста

Сессия может оборваться в любой момент. Порядок восстановления:

1. Прочитай **`docs/handoff.md`** — текущее состояние: на чём остановились, что
   в работе, что сломано, что проверено.
2. Прочитай **`docs/backlog.md`** — записи владельца: чего он хочет.
3. При необходимости — **`docs/architecture.md`** (устройство пакета изнутри:
   из чего собран узел, путь одного нажатия, что легко сломать обратно) и
   **`docs/records/`** (история правок, если она уже заведена).
4. Сверь с репозиторием: `git log --oneline -10`, `git status`.

Пока не прочитан `docs/handoff.md`, никаких правок в коде.

## 2. По ходу и в конце сессии — поддержание состояния

**`docs/handoff.md` должен быть актуален всегда**, а не только в конце: сессия
обрывается без предупреждения, и всё, что не записано, теряется. Обновляй его,
когда сделан заметный шаг (коммит, пройденная проверка, найденный дефект),
когда меняется направление работы, перед длинной операцией и в конце сессии —
обязательно.

Чего в `handoff.md` быть не должно: пересказ истории коммитов, разбор уже
законченных эпизодов (это `docs/records/`), пожелания владельца (это
`docs/backlog.md`).

## 3. Бэклог владельца

`docs/backlog.md` — то, что владелец хочет сделать. Правила:

- следи за ним и **сам предлагай взять пункт в работу**, когда текущая задача
  закончена или пункт оказался по пути;
- взял и выполнил — **удали пункт из бэклога** в том же коммите, что и работу;
- выполнил частично — оставь пункт и сократи его до оставшегося;
- не переписывай формулировки владельца без нужды, не удаляй невыполненное.

## 4. История правок — `docs/records/`

Спеки, планы, отчёты, разборы дефектов. Каталог заводится первой записью;
пока её нет, история этого пакета лежит в записях scopo, откуда он вырос
(`2026-08-24[1]`…`[3]` там). Правила те же, что в scopo:

- имя файла **`YYYY-MM-DD[N]-name-kind.md`**, квадратные скобки — литеральные;
  `[N]` — порядковый номер записи за день, начиная с `[1]`;
- **`kind` в конце имени обязателен**: `design` (устройство и API), `plan`
  (план работ), `report` (отчёт о сделанном), `review` (полное ревью проекта),
  `log` (сырой журнал прогона);
- каждый файл начинается с H1 и **шапки текущего состояния** сразу под ним:
  что с этой работой сейчас, одна фраза о содержимом, имена связанных записей;
- шапку обновляют, когда состояние работы изменилось; сам текст записи не
  переписывают — он исторический;
- **у каждой проработанной находки ревью — вердикт абзацем в конце неё, в самом
  файле ревью**, с жирным зачином: `**Вердикт: исправлено.** …`;
- документы в `docs/records/` не поддерживаются как справка: расходятся с
  кодом — верен код.

## 5. Git

- **Мержим прямо в `main`, без PR.**
- **Не коммить чужие правки вместе со своими.** Перед коммитом — `git status`
  и `git diff`; коммить свои файлы поимённо, а не `git add -A`.
- Сообщения коммитов на английском, с префиксом: `feat:`, `fix:`, `docs:`,
  `refactor:`, `test:`, `chore:`.
- Не публиковать пакет (`dart pub publish`) без явной просьбы владельца.
- **Публикация закрывает окно ломающих правок**: до неё переименовать или убрать
  публичное имя стоило ноль, после — стоит версии, и решает это владелец.

## 6. Проверки

Тулчейн — **Flutter 3.27.0 через fvm** (`.fvmrc`, `.fvm/` и
`.vscode/settings.json` не под контролем версий). Это ровно тот пол, что
заявлен в `pubspec.yaml`: команды ниже и есть проверка пола.

```sh
fvm flutter test                     # все зелёные; число — в docs/handoff.md
fvm flutter analyze                  # корень; обходит и example/
fvm dart format --set-exit-if-changed lib test
fvm dart doc --dry-run               # 0 warnings, 0 errors
fvm dart pub publish --dry-run       # 0 warnings
sh docs/ru/check.sh                  # переводы отвечают оригиналам
(cd example && fvm flutter analyze && fvm flutter test)
```

Перед мержем в `main` проходят все семь. Утверждать «работает» без вывода
команды нельзя: сначала прогон, потом заявление.

**Прогнал что-то другим SDK** — глобальным `flutter` с `PATH` или через
`fvm spawn <версия>` — сразу после этого `fvm flutter clean && fvm flutter pub
get`: чужой движок оставляет в `.dart_tool` свой кеш, и следующий прогон падает
на `Asset 'shaders/ink_sparkle.frag' ... Expected 2, got 0`. Дефекта в коде при
этом нет.

**`docs/` не публикуется** — исключена в `.pubignore` вместе с `AGENTS.md` и
`CLAUDE.md`. Сьюта тоже: 58 КБ против 26 КБ `lib/`, и потребителю она не нужна.

## 7. Язык

- Документы для владельца и агентов (`AGENTS.md`, `docs/`) — **по-русски**.
- Публичные артефакты — **по-английски**: `README.md`, `CHANGELOG.md`,
  dartdoc-комментарии, сообщения коммитов, тексты ошибок.

**Русские зеркала публичных документов** — в `docs/ru/`, по путям оригиналов:
`docs/ru/README.md`, `docs/ru/example/README.md`. Правка оригинала не
заканчивается без правки перевода **в том же коммите**; после правки —
`sh docs/ru/stamp.sh` (переносит blob-хеш оригинала в шапку перевода),
расхождение ловит `sh docs/ru/check.sh`. Комментарии внутри примеров кода в
зеркалах тоже переводятся, кроме директив `// ignore: …`.

`stamp.sh` не читает текст и не отличит обновлённый перевод от устаревшего.
Запуск «чтобы гейт замолчал» — это ложь в проверке, а не её прохождение.

## 8. Как здесь принято работать

- **Сначала тест.** Дефект — сперва падающий тест, потом исправление.
  Исправил — откати правку и убедись, что тест падает.
- **Не расширяй объём молча.** Нашёл смежную проблему — запиши в
  `docs/handoff.md`, а не чини заодно.
- **Отчитывайся честно.** Тесты упали — покажи вывод.
- Правки в `lib/` без обновления `CHANGELOG.md` не заканчиваются.
